- **Scope:** everything planned for public deployment:
  - `apps/server`: Fastify API, WebSocket hub and indexer;
  - `apps/web`: React + Vite;
  - `packages/sodex-core`: signing;
  - `packages/copy-contract` and `contracts/`: the copy registry, not deployed;
  - dependencies, repo hygiene and the production hosting plan.
- **Baseline:** commit `983eb85`, plus the uncommitted work of the concurrent agents as of the afternoon of 2026-09-30.
- **Method:** a read-only review first, then fixes. Fixes are limited to the files this audit owns, and every fix has **no effect on the UI or the user's experience**.
- **Parallel reviews:** the Solidity code and the web page's DOM sinks were reviewed in parallel, and their claims were verified before being included.
- **Line numbers:** they refer to the code **before** the fixes (983eb85). Web line numbers are those of the working tree reviewed.

**Severity scale:**

- **Critical:** funds, or a key that can move them, at risk with no precondition.
- **High:** a realistic attack in the planned deployment.
- **Medium:** needs a precondition, or leaks data across users.
- **Low:** defence in depth.
- **Info:** noted; no action needed.

### Headline

- **Nothing critical.** No server ever holds a key that can move funds, and none was reachable.
- **Three problems made the planned deployment unsafe:**
  1. The "custodial routes answer 410" guarantee could be bypassed with percent-encoding (S-01).
  2. The server had no public-hosting mode at all (S-02).
  3. The copy SDK let anyone silence any leader for every follower (C-1). This is latent: no code calls the SDK yet.
- **All three are fixed:**
  - `VALUESCAN_HOSTED=1` now turns the server into a locked-down, read-only index API (§1.1).
  - Production headers and TLS are specified in `docs/deploy/SECURITY-HEADERS.md`.
  - `npm audit` reports 0 vulnerabilities.

### Where the 3 open items live

- **K-02 (medium, design):** the persisted browser trading key. The code-side mitigations are
  in place. What is left is the owner's UX call on the key's lifetime and on "remember this
  device".
- **S-12 (low):** a loopback Host check against DNS rebinding. It is waiting on the user.
- **D-02 (low):** `git rm apps/web/package-lock.json`.

Info items stay open too: C-3 and C-4, which are contract changes before any deployment, and
the C-5 notes on `INTEGRATION.md`. The first-round routing table is kept in §9.

## 1. Server (`apps/server`)

### 1.1 Hosted mode: what was built

`VALUESCAN_HOSTED=1` is implemented in `apps/server/src/hosted.ts`, and wired in `index.ts` and `config.ts`. With the switch off, local dev behaves exactly as before. The local smoke test in section 8 confirms it.

#### Route allow-list (`HOSTED_ROUTES`)

- Routes are matched on the route **pattern** the router picked (`req.routeOptions.url`), so no encoding trick can get around it.
- Every route not on the list answers 404, even if a plugin registered it.
- There are 23 routes, **all GET**:
  - 9 index routes: health, leaderboard, explore, the 5 cohort routes, and the screener;
  - 14 marked `provisional`, because the current web still calls them.
- The whole list was **PROVISIONAL** in round 1. It is now final, per `docs/ARCH-traffic.md` §5: 16 routes, see §11.
- The SoPoints sign-in relay is **not** on the list. The points page is not mounted (the router sends `points` to `trade`). If a state-changing route is ever added, the gate already requires the exact site `Origin` and applies the `auth` limits.

#### Custodial code off, whatever the environment says

- `SERVER_SIGNING` and `ALLOW_ENV_KEY` are forced to false.
- The `trade`, `wallet` and `money` plugins are never registered.
- Custodial paths still answer 410.

#### No local token

Nothing mints or checks it in hosted mode.

#### Per-client rate limits

- Each client is keyed by the address Fastify derives through `trustProxy`. That trusts `X-Forwarded-For` only from the configured proxy hops (`VALUESCAN_TRUST_PROXY`); trusting everyone is refused.
- IPv6 clients are grouped by /64.
- There are three classes: `read`, `upstream` and `auth`, plus a global `auth` cap.
- The limiter's memory is bounded.

#### Everything else

- **CORS** answers only `VALUESCAN_ALLOWED_ORIGINS`: no loopback origins, no `DELETE`.
- **The WebSocket hub is off:** neither the hub nor `/ws` is registered.
- **`/api/health` is minimal:** `{ok, network, chainId, mainnetWritesAllowed}`, which is exactly what the web reads.
- **API response headers** add HSTS and a deny-all CSP.
- **Request limits:** 16 KiB bodies, a 30 s request timeout, and a 400 for a repeated query parameter.
- **Logging:** request logs keep the path only.
- **Optional `VALUESCAN_ORIGIN_SECRET`** requires `X-Origin-Verify` on every request except `/api/health`, so nobody can bypass CloudFront by calling the instance directly.

The environment variables are listed in §10 and in `docs/deploy/SECURITY-HEADERS.md` §2.

### 1.2 Findings

#### S-01 · High · The custodial 410 gate can be bypassed with percent-encoding
- **Component:** server request gating.
- **Where:**
  - `apps/server/src/index.ts:58-74`: `isServerSigningPath(req.url.split('?')[0])`;
  - `index.ts:250`: `classify(req.url…)`.
- **Exploit:**
  1. The router (find-my-way) matches the **percent-decoded** path, but the gate tested the raw URL. So `POST /api/%73ession/import` reaches the `/api/session/import` handler while `SERVER_SIGNING=0`. Reproduced on Fastify 5.12.1.
  2. That handler installs a signing key, and `/api/%74rade/perps/order` then signs orders from the server.
  3. Locally this needs the local token. A public deployment would need `VALUETRADE_REQUIRE_TOKEN=0` (browsers get no Vite proxy to inject the token), and a missing `Origin` is accepted. So any `curl` could make the server hold keys and relay trades again, which breaks the invariant "a hosted server can never hold a key".
  4. The same trick also moved money routes out of the `money` rate-limit class.
- **Fix:**
  - `isServerSigningRequest` and `installServerSigningGate` (in `hosted.ts`) test the raw path **and** the matched route pattern.
  - The rate-limit class is now taken from `req.routeOptions.url`.
  - Hosted mode never registers the custodial plugins.
- **UX impact:** none. The web never sends encoded paths, and the gate's answer (410) is unchanged.
- **Status:** **Fixed.** Covered by:
  - `hosted.test.ts`: "custodial paths are recognised…" and "gate: custodial paths answer 410, percent-encoded or not";
  - `limits.test.ts`: "money classification…";
  - the local smoke test and the live :8797 after the swap, where an encoded `session` path now gets 410.

#### S-02 · High · The server has no safe way to be public
- **Component:** the server's authentication model and route surface.
- **Where:**
  - `index.ts:1-7`: the loopback-only design;
  - `index.ts:232-262`: Origin and token checks run on non-GET requests only;
  - `localToken.ts:82`;
  - the route plugins at `index.ts:151-172`.
- **Exploit:** serving browsers from a public host needs `VALUETRADE_REQUIRE_TOKEN=0`. That exposes every route to everyone:
  1. **Per-user exchange proxies** (`/api/acct/*`, `/api/md/*`, `/api/scan*`, `/api/wallet/account`, `/api/money/overview`, `/api/deposit/*`, `/api/mirror/*`) run on the server's single IP and weight budget. A few clients can get that IP rate-limited by SoDEX's Cloudflare (1015). The indexer shares that IP, so it stalls for everyone.
  2. **`/api/stats/all-time?address=…&rebuild=1`** starts a multi-minute history walk for **any** address, and the in-flight map has no bound (`history.ts:1157-1186`).
  3. **`POST /api/scan/track`** starts background polling, and that state is **global**. Anyone can list, stop or fill the 6 slots of every other user (`routes/scan.ts:431-460`).
  4. **The WebSocket hub** has no parameter validation, a 100 MiB frame size and no connection cap. One visitor can take all 6 per-wallet account connections (`sodex/ws.ts:318`).
  5. **`/api/health`** leaks data (S-03).
- **Fix:** hosted mode (§1.1).
- **UX impact:** none. Local dev is unchanged.
- **Status:**
  - **Fixed** (the mechanism). The allow-list stays provisional until `docs/ARCH-traffic.md` exists.
  - Tests: `hosted.test.ts` ("gate: listed routes answer, everything else is a 404…", "the allow-list holds no custodial, per-user-proxy…", "…hosted mode is read-only"), plus the hosted smoke test.

#### S-03 · Medium · `/api/health` exposes other users' wallets and internals
- **Component:** the `/api/health` route.
- **Where:** `index.ts:127-149`, `hub.ts:257-262` and `sodex/ws.ts:380` (`accountStats()` includes `user`).
- **Exploit:** on a shared server, anyone polling `/api/health` sees:
  - `hub.accounts[].user`, the wallet of every user whose account stream is open right now: who is online, and when;
  - upstream URLs, the REST weight budget and the subscription counts.

  That is a cross-user privacy leak, and personal data under GDPR.
- **Fix:** hosted mode returns only `{ok, network, chainId, mainnetWritesAllowed}`. Production builds read `network` and `mainnetWritesAllowed` (`trading/config.ts:101`); `weightSpent` and `hub` are read only in DEV builds (`StatusFooter.tsx:187`).
- **UX impact:** none.
- **Status:** **Fixed** (hosted). The local response is unchanged, since that data is local-only there.

#### S-04 · Medium · No per-client rate limiting and no trust-proxy handling
- **Component:** `rateLimit.ts`.
- **Where:**
  - `rateLimit.ts:45-64`: one global bucket per class, and writes only;
  - `index.ts:40-43`: no `trustProxy`.
- **Exploit:**
  1. Reads are unlimited. Per-address reads cost upstream calls: `/api/vs/trader|fills|account`, `/api/vs/price` per coin, leaderboard search, and the `/api/external/*` lookups.
  2. So one client iterating over addresses drains the shared Hyperliquid, SoDEX and Lighter/Arcus budgets for everyone. It also risks a venue ban on the server's IP, which stalls the indexer.
  3. A naive fix keyed on `X-Forwarded-For` would let clients forge their key.
- **Fix:**
  - `KeyedLimiter` (in `rateLimit.ts`) adds per-client fixed windows, with a sweep and a key cap that evicts the oldest entry.
  - Hosted limits, per client unless noted, all configurable:
    - `read`: 600/min;
    - `upstream`: 120/min;
    - `auth`: 20/min per client, plus 300/min overall.
  - The client is `req.ip` under `trustProxy`, and `true`/`*` is refused at boot.
  - IPv6 clients are grouped by /64.
- **UX impact:** none. The limits are about 10× the web's heaviest polling (the 5 s tape, 15–60 s panels, 30 s Scan). Local mode keeps its write and money limits.
- **Status:** **Fixed.** Tests:
  - `limits.test.ts`: 4 limiter tests;
  - `hosted.test.ts`: per-client limit and Retry-After, the IPv6 /64 grouping, the `upstream` and `auth` classes, and two proxy tests.
- **Residual:** floods from many addresses. The WAF rule in `SECURITY-HEADERS.md` §2.4 covers them.

#### S-05 · Medium · Route caches keyed by caller input grow without bound
- **Component:** `routes/external.ts` and `routes/scan.ts`.
- **Where:**
  - `routes/external.ts:156-172`: keyed by caller-chosen `page`, `lang`, `label`, announcement `id` and wallet address, with no eviction;
  - `routes/scan.ts:39-49`: one entry per wallet.
- **Exploit:**
  - `GET /api/external/announcements/1…N`, or `/leaderboard/rank` with random wallets, adds one permanent entry per request until the process runs out of memory.
  - `lang` and `label` were unbounded strings, forwarded upstream.
- **Fix:**
  - Both caches are bounded (external 500, scan 200). Entries older than the longest TTL are evicted first, then the oldest.
  - `lang` must be a language tag.
  - `label` is capped at 64 characters.
  - `page` is capped at 1,000, which is all SoDEX publishes.
- **UX impact:** none. The web sends `lang=en`, short labels, and pages 1–100.
- **Status:** **Fixed.** Tests: `routeHardening.test.ts`, 2 tests.

#### S-06 · Medium · The on-chain resolver's cache is unbounded
- **Component:** `sodex/chain.ts`.
- **Where:** `sodex/chain.ts:568` (`onchainCache`, never pruned) and `:584`. It is reached by `GET /api/external/resolve-account` and `/api/feed/account`, both provisional hosted routes.
- **Exploit:** each new account id costs 2–3 RPC calls plus one sodex.dev call, and adds a permanent entry. At the hosted `upstream` limit, one IP can add about 170,000 entries a day.
- **Fix (proposed):** prune it like the other caches: cap it at about 5,000 entries and evict expired ones first. Alternatively, drop both routes from `HOSTED_ROUTES` once the web no longer needs them.
- **UX impact:** none.
- **Status:** **Open.** The file is under `sodex/*`, which the browser-direct agent is refactoring. Mitigated by the hosted `upstream` limit.

#### S-07 · Low · `/api/money/overview` puts an unvalidated address into a gateway path
- **Component:** `routes/money.ts`.
- **Where:** `routes/money.ts:111-118`.
- **Exploit:** `address=../../v1/perps/markets/symbols%3F` walks to **any** GET endpoint on `mainnet-gw.sodex.dev`, using this server's IP and budget. It cannot reach another host.
- **Fix:** the address must be `0x` followed by 40 hex characters.
- **UX impact:** none. The web always passes the connected wallet's address.
- **Status:** **Fixed.** Test: `routeHardening.test.ts`. The plugin is not registered in hosted mode.

#### S-08 · Low · The WebSocket hub has 100 MiB frames, unvalidated parameters and no connection cap
- **Component:** the WebSocket hub.
- **Where:**
  - `index.ts:75`: the ws default `maxPayload` is 100 MiB;
  - `hub.ts:80-97,123-150`: `symbol` and `symbols` are forwarded upstream with no size limit;
  - `hub.ts:219`: no client cap;
  - `sodex/ws.ts:318`: the 6 account connections are shared by all clients.
- **Exploit:** with the token, a client can send one 100 MiB frame, or a `symbols` array with millions of entries, which costs CPU and memory in `subKey`. It can also hold all 6 account connections.
- **Fix:** `maxPayload` is now 64 KiB (client operations are under 1 KiB). Hosted mode does not register the hub at all.
- **UX impact:** none.
- **Status:** **Fixed.** In the local smoke test a 70 KiB frame is closed with 1009, and ping/pong is unchanged.

#### S-09 · Low · CORS allows any loopback port, and `DELETE`
- **Component:** CORS configuration.
- **Where:** `index.ts:45-50`.
- **Exploit:** on a public server, a malicious page on a visitor's own `localhost` could read API responses cross-origin.
- **Fix:** hosted mode allows exactly the normalised `VALUESCAN_ALLOWED_ORIGINS`, with GET/POST/OPTIONS only.
- **UX impact:** none.
- **Status:** **Fixed** (hosted). Local mode is unchanged. Test: "gate: CORS answers the site origin only".

#### S-10 · Low · Query strings with wallet addresses reach the logs
- **Component:** request logging.
- **Where:** `index.ts:40-41`. Fastify's default request serializer logs the full `req.url`.
- **Exploit:** a public server would log IP-plus-wallet pairs for every visitor, with no retention rule.
- **Fix:** in hosted mode the request serializer logs the method, the path and the client address only. `SECURITY-HEADERS.md` §2.5 sets log retention at 14 days or less.
- **UX impact:** none.
- **Status:** **Fixed** (hosted).

#### S-11 · Low · Internal and upstream error text reaches callers
- **Component:** error handling in the routes.
- **Where:**
  - `routes/valuescan.ts:97-102`: `fail()` returns `err.message`;
  - `:74`: `?venue=a&venue=b` produces `q.venue.toLowerCase is not a function`;
  - `routes/external.ts:134-141`: up to 160 characters of the upstream body.
- **Exploit:** internal errors and upstream URLs are disclosed. 5xx responses were already generic (`index.ts:113-122`).
- **Fix:** hosted mode answers a repeated query parameter with 400, which removes the TypeError class.
- **UX impact:** none.
- **Status:** **Fixed** (the actionable part). Upstream error text still passes through by design, because the UI shows the venue's reason.

#### S-12 · Low · DNS rebinding can read local GET routes
- **Component:** local mode.
- **Where:** `index.ts:232-262`. The Host header is never checked, and GET requests need neither Origin nor token.
- **Exploit:** a page that rebinds its hostname to 127.0.0.1 can read local GET responses.
  - With `SERVER_SIGNING=0`, that is only the tracked-wallet list and `/api/health`.
  - With `SERVER_SIGNING=1`, `/api/health` also gives the paths of the token file and `.env`, and the active address.
- **Fix (proposed):** in local mode, accept only loopback or `*.localhost` Host headers, as Vite 6 already does for :5180.
- **UX impact:** none for the normal setup, but it changes behaviour for tunnels or custom hostnames.
- **Status:** **Open.** The owner has to decide, since "local dev must behave exactly as today".

#### S-13 · Info · Environment defaults
- **Where:**
  - `config.ts:104`: `VALUETRADE_ALLOW_MAINNET` defaults to on;
  - `localToken.ts:82`: the token is required by default, which is good.
- **Notes:**
  - `mainnetWritesAllowed` also turns on the **browser's** mainnet trading (`trading/config.ts:111-112`), so that default is a product decision.
  - Hosted servers hold no keys, so the flag is only advisory there.
  - Hosted mode forces `SERVER_SIGNING` and `ALLOW_ENV_KEY` off. If `SODEX_PRIVATE_KEY` is set anyway, the existing "IGNORED" warning fires.
- **Recommendation:** set `VALUETRADE_ALLOW_MAINNET` explicitly on the hosted instance.

#### S-14 · Info · The SoPoints sign-in relay forges `Origin` and passes a JWT through
- **Where:**
  - `routes/pointsAuth.ts:68-88`: sends `Origin: https://sodex.com` and follows redirects;
  - `:99`, `:118`: passes the upstream status through.
- **Notes:**
  - The relay exists because `sodex.com/auth` answers CORS only for its own origins.
  - The ~15-day SoDEX identity JWT passes through the server, which neither stores nor logs it. The `points.ts` comment says otherwise; see W-11.
  - The relay is **not** exposed in hosted mode, since the points page is unmounted.
- **If it comes back:** ask SoDEX to allowlist the production origin rather than relaying.

#### S-15 · Info · Leaderboard reads steer the indexer's priorities
- **Where:** `routes/valuescan.ts:141-144,178` (`watchAddresses`).
- **Notes:** paging through a leaderboard pushes real, already-public traders into the indexer's watch queue. The queue is bounded to 300 per venue (`engine.ts:390-405`), so the effect is priority skew at most.

#### S-16 · Low · The Lighter/Arcus request pacer queues without bound
- **Where:** `valuescan/extra/http.ts:56-78`. Every call chains onto a single promise.
- **Exploit:** a burst of per-address reads builds an unbounded queue, and every later user waits behind it.
- **Fix (proposed):** refuse new requests beyond a queue depth of about 50, with a quick "busy" answer.
- **UX impact:** none under normal load.
- **Status:** **Open.** The file is under `valuescan/*` (browser-direct agent). Mitigated by the hosted `upstream` limit.

#### S-17 · Low · The SoDEX REST response cache never evicts
- **Where:**
  - `sodex/rest.ts:270-295`: `/klines` paths carry caller-chosen `startTime`/`endTime`, and each one is cached forever;
  - `sodex/lastGood.ts:47`: the row cap is enforced on only 2% of writes.
- **Reach:** the local API only. `/api/md/*` is not a hosted route.
- **Fix (proposed):** use the same sweep and cap as `valuescan/hyperliquid/info.ts:206-259`.
- **UX impact:** none.
- **Status:** **Open.** The file is under `sodex/*` (browser-direct agent).

#### S-18 · Info · Checked and found sound
- **SQL.** Every query in `indexer/store.ts`, `history.ts` and `sodex/lastGood.ts` binds its parameters. The only interpolated fragments are constants:
  - `ORDER_KEY`, `DAY` and `ASC`/`DESC`;
  - lists of `?` placeholders sized from the validated venue list;
  - migration column names from `ADDED_COLUMNS`.

  There is no SQL injection, and no indexer change was needed.
- **SSRF.** No server fetch takes a host from the caller: every base URL is a constant or an operator environment variable.
  - Addresses, ids and coins are regex-checked, or passed through `URLSearchParams`/`encodeURIComponent`.
  - `pointsAuth` posts to a fixed path on a fixed host.
  - `mirror.ts` sends a validated address and chain key to fixed hosts.
  - The one unvalidated path splice was S-07.
- **Path traversal and static serving.** The server serves no files, and `@fastify/static` is not installed.
- **Prototype pollution.**
  - Fastify rejects `__proto__` and `constructor.prototype` in JSON bodies with a 400 (probe: `FST_ERR_CTP_INVALID_JSON_BODY`).
  - The query parser is flat: `a[b]=` stays a literal key.
  - Request data is never deep-merged: `scrubDeep` only writes `label`.
- **Error and stack leakage.** 5xx responses carry a fixed string, and the full error goes only to the server log. A 404 is JSON with `nosniff`.
- **Existing gates.** `origin.ts` parses the URL, so there are no substring tricks. The token compare is constant-time.
- **Signing.** `apps/server/src/signing/*` is used only by the disabled custodial path, and it is pinned to Go SDK vectors.

#### S-19 · Low · The GET that starts history walks can be fired cross-site
- **Component:** `routes/stats.ts` (found by the web sweep).
- **Where:** `routes/stats.ts:213-218`. A GET with side effects: it starts a history walk for any address, and `rebuild=1` discards the cached history.
- **Exploit:**
  1. Any website the user visits embeds `<img src="http://127.0.0.1:5180/api/stats/all-time?address=…&rebuild=1">`.
  2. A no-cors GET passes the origin gate, and through the Vite proxy it even carries the local token.
  3. The attacker can burn the user's SoDEX budget from their own IP and wipe their cached history.
- **Fix:** the route answers 403 when `Sec-Fetch-Site` is `cross-site` or `same-site`. The app's own reads are `same-origin`, and native clients send no such header.
- **UX impact:** none.
- **Status:** **Fixed.** Test: `routeHardening.test.ts` ("stats: the side-effecting GET refuses cross-site…").

## 2. Signing (`packages/sodex-core`) and browser keys

#### K-01 · Info · Signing correctness and replay protection are sound
- **Where:** `packages/sodex-core/src/eip712.ts`, `network.ts`, `nonce.ts`, `keys.ts` and `registration.ts`.
- **Exchange actions.**
  - The domain is `{name: 'spot'|'futures', version: '1', chainId: 286623|138565, verifyingContract: 0x0}` (`eip712.ts:137-157`). A signature therefore cannot be replayed across engines (spot vs perps) or across networks (testnet vs mainnet).
  - The signed struct is `ExchangeAction(bytes32 payloadHash,uint64 nonce)`, where the payload hash covers the Go-JSON of `{type, params}`, so a signature cannot be moved to another action.
  - The output is byte-identical to the Go SDK: 159/159 tests pass, including the SDK vectors.
- **Replay.**
  - SoDEX keeps the 100 highest nonces per signer, within a (T−2d, T+1d) window.
  - `nonce.ts` issues strictly increasing nonces across tabs, using Web Locks, a high-water mark in localStorage and a BroadcastChannel, and a clock fence. It enforces the window with a 60 s margin.
- **Keys.**
  - Keys come from the CSPRNG and are checked for scalar validity (`keys.ts:28-50`).
  - A key lives at most 7 days, and "never expires" is refused for browser keys (`keys.ts:131-167`).
  - A wallet-signed registration is recovered and checked against the expected master wallet before it is sent.

#### K-02 · Medium · The persisted browser trading key is only as safe as the page
- **Component:** the browser key vault (design).
- **Where:**
  - `apps/web/src/trading/vault.ts:12-18,100-102,170-182,208-227`;
  - `trading/session.ts:27-31`: the key is an **ordinary** key. It can trade, change leverage and margin, and move funds between the owner's own accounts.
- **The crypto is correct:**
  - AES-GCM-256 with a fresh 96-bit IV for every seal;
  - the AAD binds the network, the owner and the key address;
  - on load the key must hash back to its registered address;
  - the wrapping key is a **non-extractable** WebCrypto key, stored as a `CryptoKey` in the same IndexedDB.
- **What it does not protect against:**
  1. **Same-origin script** (an XSS, a compromised dependency, a malicious extension). It can call the vault's own `load()` and receive the raw 32 bytes. Non-extractable only blocks `exportKey`.
  2. **Local malware that reads the browser profile.** Chromium keeps the CryptoKey material in the profile's IndexedDB files.
- **Exploit:** within the key's lifetime (up to 7 days), an attacker can drain value through self-trades against their own orders on thin markets, or force liquidations through leverage changes. They cannot withdraw to a third party (per SoDEX).
- **What can be done without changing UX:**
  - Keep `script-src 'self'`.
  - Remove the `ws:`/`wss:` wildcards (W-02), so injected code has nowhere to send the key.
  - Keep the dependency set small and pinned. AppKit is already pinned, with analytics, email, socials, onramp and swaps switched off (`walletconnect.ts:598-604`).
  - Send the production headers.
- **Options that change UX (the owner's call):** a shorter default key lifetime, or "remember this device" off by default.
- **UX impact of the implemented part:** none.
- **Status:** **Open.** It is a design risk, and it is the same model sodex.com and Hyperliquid use. The CSP part is routed to the browser-direct agent.

#### K-03 · Low · The browser takes security-relevant parameters from unauthenticated server responses
- **Where:**
  - `apps/web/src/trading/config.ts:101-118`: `/api/health.mainnetWritesAllowed` turns browser mainnet trading on;
  - `apps/web/src/trading/funds.ts:372-375,419-426,511-512`: `/api/deposit/chain` supplies the `chainId`, `rpcUrl` and `explorerUrl` used for `wallet_addEthereumChain` and for the ERC-2612/CallForPermit typed-data domain.
- **Exploit:** a compromised or impersonated API origin could:
  - have the wallet offer to add ValueChain with an attacker-controlled RPC;
  - get permits signed under a wrong `chainId`. These fail rather than steal, because the spender and the token are pinned constants.

  - Pin the ValueChain parameters in the web. They already exist as constants in `sodex-core` and in the new `sodex/chainParams.ts`.

- **UX impact:** none.
- **Status:** **Open** (browser-direct agent's files).

#### K-04 · Info · What the user is asked to sign
- **API-key registration.** It is SoDEX's `UserSignedAddAPIKeyAction`: the domain `chainId` is the wallet's current chain, and `verifyingContract` is 0x0. Any site can request such a signature.
  - Valuescan generates the key locally, so the realistic abuse is a compromised frontend substituting its own key address.
  - The defence is the integrity of what is delivered: a private S3 bucket behind OAC, no scripts from a CDN, a CSP, and deploy credentials kept apart from dev machines.

#### W-01 · Medium · Production has no clickjacking protection yet
- **Where:**
  - `apps/web/vite.config.ts:127-142`: anti-framing headers are set for the dev server and `vite preview` only;
  - `apps/web/index.html:28-31`: a `<meta>` CSP cannot carry `frame-ancestors`.

- **Exploit:**
  1. An attacker's site loads `https://<prod>/trade` in an invisible iframe.
  2. Injected wallets grant access per frame origin, so `eth_accounts` silently reattaches (`src/wallet.ts:151-162`).
  3. A decoy gets the user to click "Enable trading". The wallet popup truthfully names Valuescan's origin, and the click registers a new `valuescan-web` key, replacing the user's own.

- **UX impact:** none.

#### C-1 · High (latent) · Anyone can silence any leader for every follower
- **Where:**
  - `packages/copy-contract/src/executor.ts:137-139`: `index.isDelegatedKey(leaderOrderSigner)`;
  - `src/state.ts:200,223,490-492`;
  - enabled by `contracts/src/ValuescanCopyTrading.sol:636`, which accepts any `delegatedKey` except zero or the follower.
- **Exploit:**
  1. Mallory records one cheap subscription whose `delegatedKey` is the target leader's order signer.
  2. From then on, every fill of that leader is skipped as a "copy of a copy" for **all** of its followers.
  3. Closes are skipped too, because the cycle check runs before the reduce-only logic. Followers are left holding positions the leader has already exited.
  4. The skips look like normal entries in the published commitments.
- **Fix:**
  - `gateSignal(index, id, input, issuanceOf)` now asks the **key store**: only a key Valuescan issued signs copy orders.
  - `issuanceOf` is required, so a caller cannot forget it.
  - `isDelegatedKey` is documented as untrusted.
- **UX impact:** none. Nothing calls it yet.
- **Status:** **Fixed.** Test: `executor.test.ts`, "naming a leader's own signer as a delegated key does not silence that leader (audit C-1)".

#### C-2 · Low · A follower's key can be kept from ever being revoked or destroyed
- **Where:** `src/state.ts:494-499`.
- **Exploit:** Mallory copies a victim's `delegatedKey` from a public event into a live subscription of her own. `liveSubscriptionsUsingKey(K)` then never empties, so the victim is never prompted to revoke the key, and the executor never destroys it.
- **Fix:** `liveSubscriptionsUsingKey(key, {follower, sodexAccountId})` counts only the key owner's subscriptions.
- **UX impact:** none.
- **Status:** **Fixed.** Test: `state.test.ts`.

#### C-3 · Info · Enforce the SEC-04 leftover on-chain
- **Where:** `ValuescanCopyTrading.sol:236,761-767`.
- **Issue:** a Subscribe signed while the key's last subscription is live becomes valid once that subscription stops. Today only a UI rule prevents this.
- **Fix:** add `expectedLastVersion` to the `Subscribe` type. The type hash changes, so the SDK and the vectors must be regenerated.
- **Status:** **Open.** It needs a contract change before deployment.

#### C-4 · Info · Governance wiring in the deploy script
- **Where:** `contracts/script/DeployValuescanCopyTrading.s.sol:49-52`.
- **Issue:** the multisig is the only proposer, executor and canceller, and an EOA passed in its place silently becomes a single key.
- **Fix:**
  - `require(cfg.multisig.code.length > 0)`.
  - Grant `CANCELLER_ROLE` to an independent guardian at deploy time.
- **Status:** **Open.** Do it before any deployment.

#### C-5 · Low · SDK traps
- **Fixed:** `src/timelock.ts:188`. Without the timelock address, `describeScheduledCall` used to rate `updateDelay(0)` as "ignore", which silently re-opened the SEC-02 bypass. The address is now required, and a JavaScript caller that omits it gets an error.
- **Still open (info):**
  - `validate.ts:250-259` has no `signedLastId`.
  - `state.ts:452-457`: `nextNonce` ignores pending messages.
  - The comment at `constants.ts:179-184` contradicts SEC-04.
  - `docs/contracts/INTEGRATION.md:275,429,450` still shows the old calls, which now take one argument fewer than the SDK requires. That document has no owner in this session.
- **Tests:** 96/96 in `packages/copy-contract`: the previous 95 plus the C-1 test.

The review found the rest sound:

- **Initialisation:** `_disableInitializers` in the constructor, and an atomic `initialize`.
- **Upgrades:** UUPS `_authorizeUpgrade` is `onlyOwner`, the owner is the timelock with a 48 h delay, `onlyProxy` is kept, and the ERC-7201 slot was recomputed.
- **EIP-712:**
  - name and version are pinned;
  - `chainid` and `address(this)` are read on every call (OpenZeppelin 5.7, no cache);
  - all 8 type hashes match the SDK.
- **Nonces:** bits are only ever set, never cleared.
- **Signatures:**
  - Only low-s ECDSA signatures are accepted, and recovery can never yield the zero address.
  - ERC-1271 is used only for signers that have code, through a STATICCALL made before any state write.
- **Other:** no reentrancy surface, an O(1) kill switch, and checked arithmetic.

## 10. Hosted mode: quick reference

The full table is in `docs/deploy/SECURITY-HEADERS.md` §2.1. The variables:

- `VALUESCAN_HOSTED=1` turns it on.
- `VALUESCAN_ALLOWED_ORIGINS=https://valuescan.example` sets the CORS origins. The legacy name `VALUETRADE_ALLOWED_ORIGINS` also works.
- `VALUESCAN_TRUST_PROXY=loopback | <hops 1-9> | <IPs/CIDRs>` controls who may set `X-Forwarded-For`. `true` and `*` are refused.
- `VALUESCAN_ORIGIN_SECRET=<32 characters or more>` requires `X-Origin-Verify` on every request except `/api/health`.
- `VALUESCAN_RATE_READ_PER_MIN` (default 600), `VALUESCAN_RATE_UPSTREAM_PER_MIN` (120), `VALUESCAN_RATE_AUTH_PER_MIN` (20) and `VALUESCAN_RATE_AUTH_GLOBAL_PER_MIN` (300) set the rate limits.

Hosted mode forces these off, whatever the environment says:

- `VALUETRADE_SERVER_SIGNING`;
- `VALUETRADE_ALLOW_ENV_KEY`;
- the WebSocket hub;
- the local token.

### 11.2 `GET /api/vs/lbrow?venue=hyperliquid&address=`

This is the one index read a Hyperliquid Scan profile needs: the address's row on the
Hyperliquid leaderboard, ranked by 30-day PnL, with the rank change against the previous file.

- **Source:** it calls `hlLeaderboardRow()` (`valuescan/hyperliquid/index.ts`).
- **Validation:**
  - `venue` must be exactly one string, equal to `hyperliquid` (case-insensitive);
  - `address` must be `0x` plus 40 hex characters;
  - any other request gets a 400 before anything is read.
- **Response:** `{ ok: true, row }`, where `row` is projected to its own fields: venue,
  address, label (always null), accountValue, pnl, roi, volume, rank and rankChange. That is
  about 300 bytes. `row` is null when the address is not listed.
- **Hosted rate class:** `read`. It is a lookup in the leaderboard file already in memory,
  never a per-address upstream call.
- **Tests:** `test/lbrow.test.ts`, 3 tests (the price test there is part of §11.3).

### 11.4 The indexer's SoDEX `/trades` drip follows the measured rule

The measured rule (ARCH-traffic §2): `/trades` and `/orders/history` share **one Cloudflare
counter of about 4 requests per ~60 s per IP**, and the next request gets a 1015 block. The
safe rate is 2 per 60 s for the pair together.

- **The old cap was unsafe.** `VALUESCAN_INDEX_SODEX_TRADES` (off by default) was clamped at
  6 per minute, which trips the block.
- **The new cap:** `indexer/engine.ts` now clamps it at `SODEX_HISTORY_PAIR_PER_MIN = 2`.
  The rule is documented where the limiter lives, including that every other history reader
  on the same IP spends the same counter.
- **The lane's rest:** each lane task reads one page, and the lane then rests `cost/perMin`
  minutes. At the cap that is 30 s after each page.
- **Tests:** `test/indexerLimits.test.ts` (2 tests) pins the clamp and the 30 s rest.
